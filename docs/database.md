# 🗄️ Database, Storage, and Persistence

## 1. Current storage model

This repository does not use a relational database, document database, cloud warehouse, object-storage service, or external persistence platform.

The input is a checked-in CSV file:

```text
AirPassengers.csv
```

The notebook and CLI load the data into memory for analysis. Pandas is used to represent and manipulate the monthly series.

## 2. Input data lifecycle

1. The CSV is stored in the Git repository.
2. A local process reads the file.
3. The CLI validates required columns and monthly continuity.
4. The observations are converted into an in-memory Pandas Series.
5. Model fitting and evaluation run locally.
6. Generated results are written to the local `artifacts/` directory.

There is no central database, shared state, transaction system, user account, or remote synchronization.

## 3. Generated output files

The CLI writes the following files:

| File | Format | Purpose |
|---|---|---|
| `forecast_report.json` | JSON | Run summary, dates, diagnostic values, metrics and future forecasts |
| `backtest_predictions.csv` | CSV | Actual holdout values and model predictions |
| `future_forecasts.csv` | CSV | Future point forecasts for candidate models |
| `backtest.png` | PNG | Visualization of historical observations and holdout predictions |

All generated files are stored under `artifacts/`. The directory is ignored by Git. It is local output and may be regenerated by running the script.

## 4. Persistence limitations

The current workflow does not:
- Store historical runs in a queryable database.
- Track model versions centrally.
- Maintain an experiment registry.
- Store user preferences or access permissions.
- Synchronize artifacts across machines.
- Guarantee retention of local outputs.
- Provide backup or disaster recovery.
- Store a history of data updates.

If an experiment needs to be retained, copy the relevant artifacts into an intentionally managed research record and include the Git commit, dataset checksum, and environment metadata.

## 5. When a database might be justified

A database should only be considered if a concrete requirement emerges, such as multiple users querying many forecast runs, a governed data ingestion process, or a service that needs structured persistence.

Before introducing one, define:
- Data entities and ownership.
- Data volume and query patterns.
- Update frequency and consistency needs.
- Retention and deletion policies.
- Access control and audit requirements.
- Backup and restore objectives.
- Migration and operational ownership.
- Security and privacy requirements.

For the current single-file educational project, a database would add operational complexity without solving a demonstrated need.

## 6. Future persistence design boundary

If a future project adds persistence, keep raw source observations distinct from transformed data, training snapshots, model metadata, forecasts, and evaluation results. Record dataset and model versions with every stored prediction. Never overwrite historical forecasts in a way that destroys the ability to reproduce what was known at the time.

This is design guidance only. None of these database entities or services are implemented in the current repository.
